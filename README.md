# Релизы 1С — каталог и навигатор обновлений

[![CI and Docker](https://github.com/ant-m13/release1c/actions/workflows/docker.yml/badge.svg)](https://github.com/ant-m13/release1c/actions/workflows/docker.yml)

Веб-приложение собирает каталог конфигураций и релизов 1С, показывает материалы
версий и строит кратчайшую допустимую цепочку обновления. Данные объединяются из
онлайн-LST и `releases.1c.ru`, а управлять импортом и каталогом можно через
встроенную административную панель.

## Быстрый старт

Требуются Docker Engine, Docker Compose v2 и учётная запись ИТС с доступом к
нужным конфигурациям.

```bash
git clone https://github.com/ant-m13/release1c.git
cd release1c
cp .env.example .env
```

Сгенерируйте три разных секрета и запишите их в `.env`:

```bash
openssl rand -hex 24       # POSTGRES_PASSWORD
openssl rand -base64 36    # ADMIN_PASSWORD
openssl rand -base64 32    # ITS_CREDENTIALS_KEY
```

Для сборки из исходников оставьте `APP_PULL_POLICY=never` и запустите:

```bash
docker compose up -d --build
```

После запуска доступны:

- сайт — [http://localhost/](http://localhost/);
- административная панель — [http://localhost/admin](http://localhost/admin);
- документация API — [http://localhost/#/api](http://localhost/#/api);
- проверка состояния — [http://localhost/api/health](http://localhost/api/health).

Войдите в `/admin` с помощью `ADMIN_LOGIN` и `ADMIN_PASSWORD`, добавьте и
проверьте ИТС-аккаунт, затем откройте «Каталог и релизы» и нажмите
«Обновить все данные».

## Что умеет

### Публичная часть

- единый каталог конфигураций из LST и проектов `releases.1c.ru`;
- карточки конфигураций с историей версий, датами релизов, требованиями к
  платформе, preview-версиями, планами, исправлениями и материалами;
- метаданные дистрибутивов: имя, размер, дата публикации и SHA-512 без раскрытия
  закрытого адреса скачивания;
- поиск по названию конфигурации и номеру версии;
- калькулятор кратчайшей цепочки обновления между произвольными версиями;
- объединение явных переходов из LST и колонки «Обновление версии» на
  `releases.1c.ru`;
- лента изменений с новыми версиями, требованиями платформы, файлами,
  материалами и исправлениями;
- отдельная страница статистики по каталогу и требованиям платформы;
- публичный OpenAPI 3.0 API со встроенной Swagger UI;
- постоянные ссылки на карточки вида `#/project/Trade110`;
- семь вариантов оформления: авто, светлая, графит, океан, шалфей, песок и 1С.

### Административная панель

- дашборд состояния каталога, очередей, ИТС-аккаунтов и незагруженного архива;
- добавление, проверка, отключение, редактирование и удаление нескольких
  ИТС-аккаунтов;
- отчёт о покрытии каталога каждым аккаунтом и список аккаунтов, которым
  доступна конкретная конфигурация;
- обновление только LST, полный импорт, выборочное обновление проектов и
  принудительная проверка всех релизов;
- постоянная очередь фоновых задач с прогрессом, журналом, отменой и
  продолжением незавершённой работы после перезапуска;
- настройка приоритетов, параллельности, подробности журнала и интервалов
  умного обновления;
- просмотр и корректировка проектов, версий, материалов, видимости и
  соответствий между `releases.1c.ru` и LST;
- просмотр версий и переходов LST независимо от доступности проекта на
  `releases.1c.ru`;
- добавление, редактирование, удаление, очистка и историческое заполнение ленты;
- переносимая резервная копия каталога и восстановление из неё;
- очистка данных `releases.1c.ru` с сохранением ИТС-аккаунтов и графа LST;
- настройка домена и автоматического HTTPS через Caddy.

## Источники данных

Приложение объединяет два источника:

- `v8cscdsc.lst` с `downloads.v8.1c.ru` — конфигурации, версии, допустимые
  переходы и пути пакетов `.cfu`. Эти данные образуют основу графа обновлений;
- `/total`, `/project/...` и `/version_files?...` на `releases.1c.ru` — каталог
  продуктов, история версий, требования платформы, переходы, файлы, материалы
  и исправления.

В административный каталог импортируются все строки `/total`, в том числе
недоступные аккаунту серые строки без ссылки. Публичная карточка такого проекта
появится только после успешной загрузки его истории версий.

Для каждого включённого ИТС-аккаунта доступ проверяется отдельно, после чего
результаты объединяются. Это позволяет получить историю продукта, доступного
только части аккаунтов. Пароли хранятся в PostgreSQL в зашифрованном виде
AES-256-GCM; ключ `ITS_CREDENTIALS_KEY` остаётся в окружении сервера и никогда
не возвращается в браузер.

Приложение не скачивает, не проксирует и не раздаёт дистрибутивы 1С. В каталоге
сохраняются только метаданные файлов, SHA-512 и опубликованные 1С ссылки на
документацию и материалы. Закрытые пути загрузки с `downloads.v8.1c.ru/tmplts`
публично не показываются.

### Сопоставление источников

Проекты `releases.1c.ru` автоматически связываются с конфигурациями LST. Связь
можно изменить или удалить в карточке проекта в административной панели.

Конфигурация LST остаётся в публичном каталоге вместе со своим графом, даже
если соответствующий проект недоступен всем ИТС-аккаунтам. Самостоятельный или
несопоставленный проект `releases.1c.ru` становится публичным после успешной
загрузки его истории версий.

## Обновление данных

Полный импорт сначала обновляет онлайн-LST, затем обходит каталог и страницы
`releases.1c.ru` для всех включённых аккаунтов. Плановый запуск выполняет
отдельный `worker` по cron-расписанию из `IMPORT_CRON`.

Обновление рассчитано на большой архив:

- неизменившиеся проекты пропускаются по номеру версии и хешу страницы;
- актуальные и приоритетные конфигурации обрабатываются раньше архива;
- последняя версия по умолчанию проверяется раз в 24 часа, релизы не старше
  года — раз в 7 дней, более старые — раз в 90 дней;
- за один обычный запуск обрабатывается ограниченная пачка архивных страниц;
- незагруженный архив дозаполняется фоновыми задачами;
- ошибочные страницы остаются в постоянной очереди и повторяются с
  увеличивающейся задержкой;
- выбранные проекты обрабатываются группой в одной ИТС-сессии на аккаунт, без
  повторной авторизации и загрузки `/total` для каждой конфигурации;
- разные ИТС-аккаунты получают отдельные очереди и лимиты запросов, а карточка
  задачи показывает агрегированный прогресс и оценку оставшегося времени;
- параллельность автоматически снижается при ответах 429/502/503/504 и
  восстанавливается после стабильной работы;
- метаданные неизменившихся страниц файлов кэшируются, по умолчанию на 30 дней.

Интервалы, размер архивной пачки, приоритеты и параллельность настраиваются в
административной панели. Команда «Проверить все релизы» игнорирует интервалы и
лимит архивной пачки; без выбранных конфигураций она обрабатывает весь доступный
каталог и может выполняться долго.

## Лента изменений

Публичная страница `#/changes` показывает четыре типа событий:

- новую версию;
- изменение минимальной или рекомендуемой версии платформы;
- новый файл или материал релиза;
- новое исправление.

Первый импорт проекта создаёт базовый снимок без публикации всего существующего
архива. Все изменения, обнаруженные при следующих импортах, автоматически
попадают в ленту. Поэтому на пустой базе первоначально загруженные старые
релизы не появятся в ней сами — для этого предназначено историческое заполнение.

### Заполнение через административную панель

Откройте «Лента изменений» → «Заполнить из каталога». Можно выбрать все или
только нужные конфигурации, предварительно посмотреть объём и затем выполнить
заполнение. Там же доступны ручное добавление, редактирование даты и содержания,
удаление отдельных событий и полная очистка ленты.

Дата версии берётся из даты релиза, дата материала — из даты публикации, дата
исправления — из даты патча. Например, существующий релиз можно поместить в
ленту его исходной датой, а не датой выполнения команды. Историю прежних
изменений требований платформы восстановить из текущего снимка нельзя: такие
события появятся при следующих импортах или могут быть добавлены вручную.

### Заполнение из командной строки

Команда идемпотентна: повторный запуск обновляет созданные записи и не создаёт
дубликаты.

```bash
# все проекты releases.1c.ru
npm run backfill:changes -- --all

# одна или несколько конфигураций: ID, nick, identity key или название
npm run backfill:changes -- --config Trade110
npm run backfill:changes -- --config Trade110 --config Accounting30

# предварительный расчёт без записи в базу
npm run backfill:changes -- --all --dry-run
```

В Docker команда выполняется из образа приложения:

```bash
docker compose run --rm web node dist/releases/backfill-change-feed.js --all
```

## Запуск готового образа

GitHub Actions публикует образ для `linux/amd64` и `linux/arm64`. В `.env`
укажите:

```dotenv
APP_IMAGE=ghcr.io/ant-m13/release1c:latest
APP_PULL_POLICY=always
```

Затем запустите:

```bash
docker compose pull
docker compose up -d --no-build
```

Если пакет GHCR закрыт, сначала выполните `docker login ghcr.io`. Для
воспроизводимого развёртывания вместо `latest` можно использовать тег образа
вида `sha-0123abc`.

Подробный сценарий для VPS, включая HTTPS, обновление, откат и диагностику,
описан в [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md).

## Конфигурация

Основные переменные находятся в `.env.example`:

| Переменная | Назначение | Значение по умолчанию |
|---|---|---|
| `POSTGRES_USER` | пользователь PostgreSQL | `upd` |
| `POSTGRES_PASSWORD` | пароль PostgreSQL | обязательно изменить |
| `POSTGRES_DB` | база PostgreSQL | `upd` |
| `POSTGRES_VOLUME_NAME` | постоянное имя volume с базой | `release1c_pgdata` |
| `DATABASE_URL` | подключение при запуске Node.js вне Compose | формируется вручную |
| `ADMIN_LOGIN` | логин административной панели | `admin` |
| `ADMIN_PASSWORD` | пароль административной панели | обязательно изменить |
| `ITS_CREDENTIALS_KEY` | ключ шифрования сохранённых паролей ИТС | обязательно задать |
| `ITS_LOGIN`, `ITS_PASSWORD` | необязательный первый ИТС-аккаунт из окружения | пусто |
| `IMPORT_CRON` | cron полного импорта | `0 4 * * *` |
| `IMPORT_ON_START` | импорт сразу после запуска worker (`1`) | `0` |
| `RETRY_QUEUE_POLL_MINUTES` | проверка очереди ошибок | `5` |
| `ARCHIVE_BACKFILL_POLL_MINUTES` | фоновое дозаполнение архива | `60` |
| `DATABASE_BACKUP_MAX_BYTES` | предел загружаемой копии каталога | 20 ГиБ |
| `WEB_PORT`, `HTTPS_PORT` | внешние порты Caddy | `80`, `443` |
| `CADDY_API` | внутренний Admin API Caddy | `http://caddy:2019` |
| `APP_IMAGE` | локальный или опубликованный образ | `release1c:latest` |
| `APP_PULL_POLICY` | `never` для сборки или `always` для реестра | `never` |

`ITS_CREDENTIALS_KEY` должен содержать 32 байта в base64 или 64 hex-символа.
После сохранения аккаунтов менять ключ нельзя: без прежнего значения их пароли
невозможно расшифровать. Сохраните `.env` в защищённой внешней резервной копии.

## Управление установкой

Обновить исходники и пересобрать сервисы:

```bash
git pull --ff-only
docker compose up -d --build --remove-orphans
```

Для установки из опубликованного образа:

```bash
git pull --ff-only
docker compose pull
docker compose up -d --no-build --remove-orphans
```

Проверка состояния, журналы и остановка:

```bash
docker compose ps
docker compose logs --since=15m web worker migrate caddy db
docker compose stop
```

Удалить контейнеры, сохранив данные:

```bash
docker compose down --remove-orphans
```

Не используйте `docker compose down -v` для обычного обновления: параметр `-v`
удаляет PostgreSQL и служебные volumes Caddy.

## Резервное копирование

В «Настройки → Резервная копия каталога» можно скачать переносимый PostgreSQL
custom dump и восстановить его на другой установке той же версии. В него входят
конфигурации, граф переходов, проекты, версии, материалы, исправления, ручные
соответствия и изменения карточек.

В каталоговую копию не входят ИТС-аккаунты и пароли, настройки сервера, сведения
о доступности аккаунтов, задачи и журналы. При восстановлении локальные аккаунты
и настройки сохраняются, а доступность проектов будет рассчитана следующим
импортом.

Для полного аварийного восстановления сервера отдельно сохраняйте `.env` с
неизменённым `ITS_CREDENTIALS_KEY`, полный дамп PostgreSQL и точный тег образа.

## API

Интерактивная документация доступна на `/#/api`, спецификация — по адресу
`/api/openapi.json`. Публичный API позволяет получать:

- каталог конфигураций и версии;
- материалы релиза и исправления;
- ленту изменений;
- цепочку обновления;
- статистику каталога и его ревизию.

## Разработка

Для локальной разработки нужен Node.js 22. Установите зависимости и выполните
полный набор проверок:

```bash
npm ci
npm run check
npm run db:check
```

`npm run check` выполняет проверку типов, тесты Vitest, сборку TypeScript,
smoke-проверку парсеров и контрактов, а также проверку цветовых тем. Для работы
со схемой базы доступны:

```bash
npm run migrate       # применить миграции
npm run generate      # создать миграцию Drizzle
npm run dev           # web-сервер в watch-режиме
npm run worker        # фоновый worker
```

## Стек и архитектура

- Node.js 22, TypeScript и Fastify;
- PostgreSQL 16 и Drizzle ORM;
- Vitest для модульных тестов;
- Caddy как reverse proxy и менеджер HTTPS;
- контейнеры `migrate`, `web`, `worker`, `db` и `caddy`;
- постоянные задачи импорта и контрольные точки в PostgreSQL;
- дельта-импорт LST по SHA файла и хешам рёбер;
- BFS по объединённому графу LST и `releases.1c.ru` для поиска цепочки с
  минимальным числом шагов;
- ETag, серверный кэш и сжатие `zstd`/`gzip` для публичного каталога.

Основные точки входа:

- `src/db/server.ts` — API, публичный интерфейс и административная панель;
- `src/db/worker.ts` — плановые, ручные и повторные фоновые задачи;
- `src/db/import-lst.ts` — загрузка и импорт онлайн-LST;
- `src/releases/import-releases.ts` — импорт каталога и релизов 1С;
- `src/releases/backfill-change-feed.ts` — историческое заполнение ленты;
- `src/db/chain.ts` — расчёт кратчайшей цепочки;
- `src/db/migrate.ts` и `drizzle/` — миграции базы данных.

## Безопасность

- пароли ИТС шифруются AES-256-GCM;
- изменяющие admin API-запросы защищены проверкой Origin/Referer;
- login ограничен десятью попытками в минуту с временной блокировкой;
- изменяющие admin API-запросы ограничены 60 запросами в минуту на IP;
- тело запроса ограничено 1 МиБ;
- включены `X-Content-Type-Options`, `X-Frame-Options` и безопасная политика
  `Referrer-Policy`;
- Caddy Admin API доступен только внутри Docker-сети.

Административные сессии хранятся в памяти web-процесса, поэтому после его
перезапуска требуется войти заново.
